# Decision Engine Mapping

**Review scope:** the current `main` implementation of MCP `tools/call` and `run_recovery_canary`, the tool-governance gateway and executor, canonical governance state, recovery state/runtime, and recovery-canary evidence. This is a documentation-only review. Open PRs #132 and #133 are not part of `main` and are not treated as implemented here.

## Findings at a glance

| Design rule | Verdict | Main finding |
|---|---|---|
| 1. Identity is not authority | **Mostly satisfied** | Authenticated identity supplies attribution and token binding; separate profile, capability, health, interceptor, and approval gates decide execution. |
| 2. One decision / four outcomes; no client bypass | **Not satisfied as a unified model** | Client booleans do not grant authority, but the implementation has several decision vocabularies and no explicit `DEFER` outcome or single decision object. |
| 3. Health is necessary, never sufficient, for a write | **Satisfied for ordinary consequential tools; canary bootstrap is blocked** | The executor checks canonical recovery state and still requires action policy/approval. However, the recovery canary is classified as a write and cannot run when the missing canary is what blocks writes. |
| 4. Health/evidence are server-only; missing evidence defers | **Partly satisfied** | State and canary evidence are computed and persisted server-side, and missing evidence fails closed. Missing evidence is represented as a block/`RESTORING`, not `DEFER`; the canary path also has a bootstrap deadlock. |
| 5. Approval is action-bound and single-use | **Satisfied for the signed-token path** | HMAC claims bind actor, session, tool, argument hash, and expiry; a unique database insert atomically consumes the token before dispatch. |
| 6. Every session, memory row, receipt, and approval has exactly one owner | **Partly satisfied** | MCP sessions are namespaced by authenticated key and lexical-memory rows have `owner_id`; several state/evidence/receipt/consumption tables rely on session or actor strings rather than an explicit owner column, and anonymous chat still supplies an unscoped session with an empty memory owner on `main`. |

## 1. Identity is not authority — mostly satisfied

**Evidence.** In `app/api/mcp/route.ts`, `POST` authenticates an operator secret, OAuth session, or API key before `tools/call`; it derives `actorId` and `ownerId` from that credential rather than from a tool argument. The route checks `requireKnownToolCapability` and `canCallTool` before resolving or invoking a handler (`POST`, approximately lines 696–764). For non-operator callers, it namespaces the session under the authenticated key ID; a caller-provided session label is not accepted as an ownership credential. Diagnostic session tools reject an explicitly supplied session outside that prefix.

`lib/agents/tool_capability_registry.ts` (`requireKnownToolCapability`) fails closed for unknown names. `lib/agents/constitutional_tool_executor.ts` (`executeGovernedToolStructured`) repeats capability admission, reads server-side canonical state, applies the canonical gate, invokes the interceptor, and evaluates action policy. The actor ID is then used for audit attribution and as one claim in an approval token, not as a substitute for those checks. The `authorize_tool_action` route is operator-only, requires a registered approval-gated capability, runs the interceptor, and only then signs a token (`app/api/mcp/route.ts`, approximately lines 492–624).

**Gaps.** The guarantee applies to the inspected MCP dispatch path. It is not a repository-wide proof that every non-MCP adapter has identical identity derivation. The route uses the shared `operator` principal for operator-secret requests; the code does not identify distinct human operators behind that shared credential.

**Smallest closing change.** Keep authenticated subject/owner derivation in the transport boundary and require each additional execution adapter to pass that server-derived subject through the same capability and decision boundary. If individual operator attribution is required, replace the shared operator subject with a verified per-person identity; do not promote a client-supplied actor field.

## 2. One decision with ALLOW, DENY, NEEDS_HUMAN, DEFER; no client bypass — not satisfied as a unified model

**Evidence.** The current code does not expose a client-controlled `approved`, `health`, `recovery_state`, or `canary_passed` switch to the executor. `tools/call` validates the tool and session, derives the authenticated profile, replaces non-operator session labels with owner-prefixed IDs, and passes the resulting arguments to the governed executor. `run_recovery_canary` accepts a session ID, but the route binds the effective session and the server-side tool recomputes the state snapshot. A supplied `approval_token` is not a boolean bypass: `evaluateToolGovernance` verifies its HMAC and its actor/session/tool/argument claims.

**Gaps.** There is no single four-outcome decision type. `GovernancePolicyDecision` in `tool_governance_gateway.ts` returns `allow`, `deny`, or `approval_required`; the executor adds values such as `DENIED_BLOCKED`, `DENIED_LOCKED`, and `EXECUTION_CANCELLED_BEFORE_START`; transport branches also return JSON-RPC errors, trajectory pauses, or timeout/unknown results. There is no first-class `DEFER` outcome. Missing evidence is consequently collapsed into a denial/block, while the operator-required meaning of `approval_required` is not represented as a distinct common outcome. Separate branches, including the external-capability control plane, do not all produce the same normalized result shape.

**Smallest closing change.** Introduce one server-owned discriminated decision result with exactly `ALLOW`, `DENY`, `NEEDS_HUMAN`, and `DEFER`, plus reason/evidence metadata. Make authentication, capability, canonical health, action approval, and specialized recovery checks return or refine that result; require every side-effecting dispatcher to invoke the common boundary. Map transport errors and execution-timeout/unknown status outside the authorization outcome without translating them into `ALLOW`. Continue treating client fields only as candidate action data or cryptographic credentials to verify.

## 3. Health is necessary, never sufficient, for a write — satisfied for ordinary consequential tools; recovery canary is blocked

**Evidence.** `readCanonicalGovernanceState` in `lib/agents/canonical_governance_state.ts` reads the persisted `z_traj` and tool-session state, computes `M`, and reads evidence for the fingerprint of that exact snapshot. `canonicalExecutionAllowed` calls `recoveryCapabilityAllowed`; it blocks an uninitialized consequential session, a value below the hard floor, and non-read capabilities without the required recovery state. `executeGovernedToolStructured` calls this gate before `interceptToolCall` and `evaluateToolGovernance` (`constitutional_tool_executor.ts`, approximately lines 242–411). A healthy state alone therefore does not authorize a consequential call: the policy still requires a valid action-bound token for approval-gated risk, and the token must be consumed before the handler runs. Read-only bootstrap exceptions do not grant write capability.

**Gap: canary bootstrap deadlock.** `run_recovery_canary` is registered as `capability: 'write'` with `approvalRequired: true` (`tool_capability_registry.ts`, `SPECIAL_TOOLS`). The executor therefore asks the canonical recovery gate to authorize it as a write before the handler can probe. When the exact snapshot has no passing canary, `recoveryCapabilityAllowed` returns `RESTORING` and rejects non-read actions. But the canary is the operator probe intended to create that missing evidence. The route's `run_recovery_canary` branch is operator-only and the handler is a read probe, yet neither fact changes the capability passed to the canonical gate. A signed approval token cannot repair this because health is checked first.

**Smallest closing change.** Model the canary as a narrowly scoped recovery-verification capability that may run only for an authenticated operator and only after the server checks the non-canary prerequisites (snapshot exists, `M`/stable-count/sigma thresholds pass). Preserve the action token/interceptor checks if required by policy, keep evidence persistence in the server route, and never let this exception authorize an ordinary write. Do not simply mark the general `write` capability bootstrap-allowed.

## 4. Health and recovery evidence are server-only; missing evidence defers — partly satisfied

**Evidence.** The client does not provide the canonical C/R/S values, state fingerprint, stable count, sigma value, or a pass flag to the recovery-state evaluator. `recoverySnapshotFingerprint` in `recovery_canary_evidence.ts` hashes the session, policy version, full-precision C/R/S, stability evidence, sigma, and trajectory timestamp. `run_recovery_canary` in `lib/lex_crs_agent/tools.ts` reads canonical state on the server, checks the prerequisites, performs the diagnostic probe, and re-reads the snapshot. The `run_recovery_canary` branch in `app/api/mcp/route.ts` accepts a pass only when the internal probe returned a well-formed snapshot, the governed executor approved the probe, the current fingerprint still matches, and durable evidence can be written and read back. The evidence row binds the server-derived actor, session, receipt, status, and fingerprint. `readRecoveryCanaryEvidence` returns no pass on missing rows or database errors, so an evidence failure cannot enable a write.

**Gaps.** First, the no-evidence/error case is not an explicit `DEFER`: `readRecoveryCanaryEvidence` collapses an absent row and a storage failure to `passed: false`; `readCanonicalGovernanceState` then reports an available `RESTORING` state when the rest of its reads succeeded, and `canonicalExecutionAllowed` returns a denial. This fails closed but does not preserve the requested distinction between a known-failed decision and a decision that must wait for evidence/storage.

Second, there is an internal recovery-progress mismatch. `advanceRecoveryPlane` says it records a no-op stabilization observation, but when `M >= TAU_RECOVERY` it returns before calling `updateZTraj` (`recovery_runtime.ts`, lines 51–61). Since `n_stable` is incremented by `updateZTraj` only for a low-velocity observation (`lib/kv.ts`, `updateZTraj`), this recovery-plane path cannot itself build the missing stable count once M has crossed that threshold. The executor calls the recovery plane when `nStable < 3`, so that call may make no progress; some other governed observation must update the trajectory.

Third, the canary bootstrap deadlock described in rule 3 prevents the intended operator evidence path from reaching the probe when no current pass exists.

**Smallest closing change.** Preserve three server-side evidence states—present/pass, present/fail, and missing/unavailable—and map the last to explicit `DEFER` (while keeping writes blocked). Make the recovery-state reader surface evidence-store failure separately from an empty table. Either implement a conditional, fingerprint-safe no-op observation at/above `TAU_RECOVERY` or correct the recovery-plane contract and route users through a verified observation path that actually increments `n_stable`. Apply the restricted canary bootstrap exception from rule 3; do not accept client-reported evidence.

## 5. Approval is action-bound and single-use — satisfied for the signed-token path

**Evidence.** `createGovernanceApprovalToken` in `tool_governance_gateway.ts` signs versioned claims containing a random approval ID, actor ID, session ID, tool name, stable SHA-256 argument hash, issue time, and expiry capped at 15 minutes. `verifyGovernanceApprovalToken` uses timing-safe HMAC comparison and checks expiry, actor, session, tool, and exact argument hash. `hashGovernanceArguments` canonicalizes object key order and removes the token/approval-ID metadata before hashing.

`executeGovernedToolStructured` runs the canonical health gate and interceptor/policy checks first. It then calls `consumeGovernanceApprovalToken` before the handler. Consumption inserts the approval ID into `governance_approval_consumptions`, whose primary key makes concurrent replays conflict; only `rowsAffected === 1` proceeds. Storage errors or a duplicate fail closed. If the tool later fails or cancellation occurs after consumption, the token stays consumed and cannot be retried—this is fail-closed.

**Gap.** The table records actor/session/tool but has no explicit `owner_id`; ownership is implicit in the authenticated actor claim and MCP session namespace, rather than an owner column. That is assessed under rule 6. This `main` path is token-only; it does not include the one-tap request flow from open PR #132.

**Smallest closing change.** Preserve the signed claim and unique single-use consumption. If first-class ownership is required, add the authenticated owner to the signed claims and consumption row/predicate, without weakening the actor/session/action checks. Do not add an unsigned client approval flag.

## 6. Every session, memory row, receipt, and approval belongs to exactly one owner — partly satisfied

**Evidence.** In `app/api/mcp/route.ts` (`POST`, approximately lines 749–764), a non-operator MCP session is prefixed with the owner ID derived from the authenticated API-key/OAuth identity, independent of plan; an already own-prefixed ID is not doubled. Explicitly named foreign sessions are rejected by the three diagnostic tools. This protects session-keyed MCP state through namespacing. The operator path intentionally leaves its session ID unchanged.

Lexical memory is the strongest explicit owner-scoped area: `lib/lex_memory.ts` stores `owner_id` and includes it in semantic recall, session-history, and centroid queries; empty owner IDs do not write or retrieve. Legacy NULL-owner rows are not adopted by a caller. In contrast, `tool_receipts` in `lib/agents/governance_commit.ts` stores `session_id` and `actor_id`, not `owner_id`; `praxis_receipts` in `lib/db.ts` stores only `session_id`; `recovery_canary_evidence` stores `session_id` and `actor_id`; and `governance_approval_consumptions` stores `actor_id`, `session_id`, and tool name. `z_traj` and `tool_sessions` are keyed by session ID. These are associated with a caller through the session prefix and, for some rows, actor ID, not an explicit owner foreign key.

**Gaps.** On current `main`, the anonymous streaming route still consumes the client `session_id` as its session key and passes `owner_id: ''` to `retrieveSessionHistory`, `retrieveSimilar`, `getSessionCentroid`, and `storeMemory` (`app/api/lex/govern/stream/route.ts`, `POST`). The empty-owner memory functions fail closed, so this prevents memory continuity, but other session-keyed state and chat receipts still use the unprefixed client label. Two anonymous browsers can therefore address the same session-scoped kernel/receipt keys if they choose the same label. The cookie-owner/session namespace change is proposed separately in PR #133 and is not included in this `main`-based review.

The gap also exists beyond streaming chat. `app/api/lex/govern/route.ts` optionally authenticates an API key and passes its ID as `owner_id` for lexical-memory operations, but continues using the raw body `session_id` for governance/kernel state and `writeKernelReceipt`. `app/api/lex/kernel/route.ts` uses the raw client session for kernel state and receipts and passes an empty owner to memory. Thus owner-scoped semantic memory does not by itself owner-scope the other per-session state or receipts on these routes.

Also, `actor_id`/session-prefix conventions are not explicit `owner_id` constraints on receipt, canary, approval-consumption, trajectory, or tool-session rows. Old unprefixed rows are not intrinsically attributable to a modern owner. The shared operator principal and unprefixed operator path do not distinguish individual humans if more than one operator uses the same secret.

**Smallest closing change.** Derive anonymous ownership from a server-set first-party cookie and namespace the session before every read/write in the streaming, JSON governance, and kernel routes (PR #133 covers streaming chat); keep owner-scoped memory queries and leave legacy ownerless rows inaccessible. For the remaining durable governance tables, thread the authenticated owner ID through state, receipt, evidence, and approval persistence; add `owner_id` columns and owner predicates/unique constraints to reads and writes. Treat pre-migration rows as unowned rather than guessing or backfilling ownership from client-supplied session labels. Retain session namespacing as defense in depth. If operator-level uniqueness is required, use a verified operator subject instead of the shared literal principal.

## Review limitations

This mapping is limited to the listed MCP/governance/recovery flow and the directly inspected persistence definitions. It does not claim that every alternate API, external capability adapter, or deployment's database schema/migrations have been exhaustively audited. The findings above distinguish fail-closed behavior from the stricter requested semantic outcome (notably `DEFER`) and identify the concrete canary-bootstrap and anonymous-session gaps visible in `main`.
